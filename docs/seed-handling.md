# シード文字列の扱い（ドメイン別の違い）

シードは盤面生成では常に原文文字列のまま扱う（`"007"` ≠ `"7"`）。
鍵導出では、ドメインによって正規化の有無が異なる。どちらも意図した設計であり、
仕様の変更ではない。

## Backup ドメイン：正規化する

- 暗号化バックアップ（CMA1）の鍵導出には `canonicalSeedKey` を使う
  （`shared/validation/seed-key.js`、`contents/qwerty/index.js` の
  `canonicalBackupSeed`）。
- 数字シードは数値として正規化される：`"007"` → `"7"`、`"0007"` → `"7"`。
  英数字シード（v2）は trim 済み文字列そのまま。
- したがって `"007"` で作った暗号化バックアップは、復号時の入力が
  `"007"` でも `"7"` でも復号できる。復号後の入力欄は、平文ボディ内の
  原文ブロックから `"007"` として復元される。
- 盤面生成そのものは正規化の影響を受けない。復元後の入力欄が `"007"` なら
  盤面も `"007"` のものになる。

## TimeLock / TimeSecret / Vault：原文文字列を厳密に区別する

- 鍵導出は `String(seed).trim()` のみで、数値への正規化はしない
  （`contents/qwerty/index.js` の `deriveAppDomainKey`、
  `shared/backup/timelock.js` の `deriveAppDomainKey`）。
- `"007"` で作ったものは `"007"` でしか開けない。`"7"` では AES-GCM の
  認証が失敗する（シード不一致エラー）。
- シード自体は TimeLock カプセル・TimeSecret 金庫・Vault には保存されない。
  復元されるのは封印された内容（テキスト・ファイル・シークレット）であり、
  シードではない。

## 旧バージョンで保存したバックアップについて

- 旧バージョンで保存した `"007"` のバックアップ（BIP39 24単語・暗号化ともに）は、
  平文ボディに原文ブロックがないため、新コードでも `"7"` として復元される。
  旧保存時に情報が失われていたため回復不能であり、今回の修正による破壊ではない。
- 新バージョンで保存し直すと、`"007"` は `"007"` として復元される。

## 統一する場合の注意

- Backup 側を原文厳密に寄せる案と、TimeLock / TimeSecret / Vault 側を
  `canonicalSeedKey` に寄せる案がある。どちらも既存データとの互換性に
  影響するため、変更するなら独立した検証と移行計画が必要である。
  現時点では統一しない。
